# Rego to CEL migration inventory

This inventory tracks every control in the Rego catalog used for [Kubescape #2002](https://github.com/kubescape/kubescape/issues/2002). At the pinned revisions, **294 distinct Rego control IDs include 66 with a CEL policy and 228 without one**. Of the 228, 71 have a proposed implementation or compatibility test and 157 have a blocker for native admission. Each row links to the control definition and the rules that determine its findings. The counts describe the starting revisions for the migration.

## Existing policy evidence

A diagnostic adaptation of Kubescape's Rego/CEL harness exercised the library policies against the active rules and current source fixtures at these pins. It used shipped defaults, with fixture normalization for removed API versions, multi-document inputs and duplicate resource identities. **37 controls agreed on the exercised fixtures, 17 had a verdict or applicability difference, 11 compared different PSA subjects, and C-0081 had no Rego fixture.** The result concerns resource-level scanner verdicts. It does not establish native API-server behavior, comparison against each upstream expected finding, or equality under fixture-specific overrides. The pinned upstream test has its own narrower control list and vendors Rego fixtures from v2.0.33. [Upstream parity harness](https://github.com/kubescape/kubescape/blob/fc41d73e9d5399120283ea19c54af8801546a8e4/core/pkg/opaprocessor/processorhandler_regocelparity_test.go) · [Fixture provenance and normalizations](https://github.com/kubescape/kubescape/blob/fc41d73e9d5399120283ea19c54af8801546a8e4/core/pkg/opaprocessor/testdata/regocelparity/README.md)

The upstream harness pins seven concrete resource differences as defects across three controls. C-0012 accounts for four credential fixtures, C-0013 for one non-root Deployment and C-0212 for the default Kubernetes Service and Endpoints. Other differences in the expanded diagnostic need individual investigation. C-0225 and C-0234 agreed in that run and have scope questions to investigate before changing either policy. [Upstream expected disagreements](https://github.com/kubescape/kubescape/blob/fc41d73e9d5399120283ea19c54af8801546a8e4/core/pkg/opaprocessor/processorhandler_regocelparity_test.go#L111-L170)

Four older workload policies, C-0198–C-0201, served as precedent and still need their own explicit disposition. C-0196 is the missing sibling. ## Reading and reproducing the inventory

Start with the top-level `controls/*.json` files in the pinned Rego repository. Index every `rules/*/rule.metadata.json` by its `name` field and resolve each control's ordered `rulesNames` through that index. This produces 352 references to 309 unique rules, including 82 distinct rules with `filter.rego`. The same rule can contribute to more than one control. C-0212 combines 17 rules and C-0211 combines 15. Each source rule link leads to its actual directory. An arrow after a linked name identifies a directory whose name differs. A linked **filter** is the optional resource enumerator. Consider its applicability alongside `raw.rego`. [Rego catalog](https://github.com/kubescape/regolibrary/tree/b7e57060ca90c41fe15359383245a7c62f09487c/controls) · [Rule layout](https://github.com/kubescape/regolibrary/tree/b7e57060ca90c41fe15359383245a7c62f09487c/rules)

For the CEL side, compare the unique `controlID` values to the directories containing `controls/C-*/policy.yaml` at the CEL pin. Confirm each policy's `controlId` label, its entry in `controls/kustomization.yaml`, and its README entry. Exclude the six runtime policies from the control-ID count. [Registered control policies](https://github.com/kubescape/cel-admission-library/blob/a19021a73782eebbfc9736ac16381f1f11fcc2d7/controls/kustomization.yaml) · [Runtime policies](https://github.com/kubescape/cel-admission-library/tree/a19021a73782eebbfc9736ac16381f1f11fcc2d7/runtime-policies)

- **Scan scope** reproduces the control's `scanningScope.matches`. The kinds under each rule summarize its `match` and `dynamicMatch` entries. **Workloads** means Pod, Deployment, ReplicaSet, DaemonSet, StatefulSet, Job and CronJob. The linked metadata gives the API groups and versions. The filters and rule bodies determine which matched objects enter the result.
- **Version bounds** apply to the individual rule. The minimum is inclusive and the maximum exclusive. In a local build with an empty build number, Kubescape skips rules with an upper bound. The row includes both current and historical variants wherever the control references both. Scanner aggregation and provider restrictions appear beside the rule when declared. [Kubescape selection logic](https://github.com/kubescape/kubescape/blob/fc41d73e9d5399120283ea19c54af8801546a8e4/core/cautils/datastructuresmethods.go#L67-L151)
- **Settings** lists Rego `postureControlInputs` keys from the rule metadata or rule source. The `dataControlInputs.` prefix identifies scan-supplied context. For existing configurable policies, the keys after the arrow are the actual CEL `params.settings` references. A dash means the source declares or references no setting of that type. Compare defaults, list/scalar shapes and case-level overrides when testing. [Rego defaults](https://github.com/kubescape/regolibrary/blob/b7e57060ca90c41fe15359383245a7c62f09487c/default-config-inputs.json) · [CEL defaults](https://github.com/kubescape/cel-admission-library/blob/a19021a73782eebbfc9736ac16381f1f11fcc2d7/configuration/basic-control-configuration.yaml)
- **Cases/data** counts directories in each rule's `test/` and the subset with `data.json`, in the same order as the listed rules. Zero means the pinned rule has no case directory. Fixture counts measure available inputs, including inputs for earlier scanner versions. They do not indicate passed tests.
- **Existing** links to the baseline VAP. **Agreed** and **difference** refer to the diagnostic above. The last number is the control's review batch. Each blocker belongs to batch 1 for documentation and to batch 29 for rechecking.
